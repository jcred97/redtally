# Core data model

The core business model follows the Salesforce Budget & Expense Manager's Expense Group, Category, Expense, Budget, Bank, and Expense Group Bank concepts. Salesforce metadata and sharing rules are not copied into PostgreSQL. Better Auth email/password accounts and private per-user ownership were deployed with their migration on October 25, 2026; Supabase remains only the PostgreSQL host.

Expense groups have a unique UUID `publicId` generated by PostgreSQL for public URLs. Migration `20261118010000_expense_group_public_id` assigns one to every existing group and adds a default for new groups. Numeric primary keys continue to join business records internally. Route lookup checks the current owner for both UUID URLs and legacy numeric URLs, which redirect to the canonical public ID while preserving query parameters. Apply this additive migration before deploying code that reads `publicId`.

```text
User
  -> ExpenseGroup (existing database table: Spending)
       -> Category (existing database group column: spendingId)
            -> Expense
       -> Budget (optional, one per calendar month)
       -> BankAssignment -> Bank (shared catalog)
            -> Expense (optional bank assignment)
       -> RecurringExpense (references a category and optionally a bank assignment)
            -> RecurringExpenseOccurrence -> Expense (until the expense is deleted)
```

## Models and rules

| Model | Responsibility | Integrity rules |
| --- | --- | --- |
| `ExpenseGroup` | Container for a set of expenses, categories, budgets, and bank choices | Maps to `Spending`; nullable user owner preserves unclaimed legacy groups; referenced groups cannot be deleted |
| `Category` | Classifies expenses within one group | Existing IDs, names, icons, colors, and parent IDs are preserved |
| `Expense` | Title, positive PHP amount, date, and optional merchant, Manila time, notes, and payment details | Integer centavos; nullable `merchant` up to 100 characters; nullable `timeMinutes` between 0 and 1439; category and optional bank assignment must belong to its group |
| `Budget` | Optional monthly target for a group | Positive integer centavos; month stored as a PostgreSQL DATE on the first day; unique group/month |
| `Bank` | Shared institution catalog | Unique normalized key; active flag; assigned banks cannot be deleted |
| `BankAssignment` | Enables a bank for a group and configures supported payment methods | Unique group/bank; four capabilities default to enabled; referenced assignments cannot be deleted |
| `RecurringExpense` | Schedule and next due date for an expense in one group | Same-group category and bank assignment; positive integer centavos; calendar dates with an inclusive optional end date |
| `RecurringExpenseSubmission` | Records a schedule draft and its original payload hash | A draft ID is unique within its group. Deleting the schedule preserves the claim so a late retry cannot recreate it. |
| `RecurringExpenseOccurrence` | Records that the worker posted a scheduled date | Unique schedule and due date; survives expense deletion until the schedule itself is deleted |

Application names are mapped to the existing database identifiers. These naming improvements require no additional migration or record changes:

| Application name | Physical database name |
| --- | --- |
| `ExpenseGroup` | `Spending` table |
| `BankAssignment` | `ExpenseGroupBank` table |
| `PaymentMethod` | `TransactionType` enum |
| `Expense.paymentMethod` | `Expense.transactionType` column |
| `Expense.legacyBankName` | `Expense.bank` column |

`ExpenseGroup` is the named record shown in the current **Expense Groups** navigation and list. **Spending** would fit a broader section if a future view brings together reports and expense groups. The PostgreSQL table name is `Spending`. [Current navigation](roadmap.md#purpose-and-navigation)

`PaymentMethod` contains the existing Cash, Debit Card, Credit Card, Bank Transfer, and Bank Payment choices. Expense groups expose monthly targets through `budgets`. The application model is named `Budget` to describe the business concept; its current implementation remains monthly, matching the Salesforce app. Each `budgetMonth` must be the first day of its calendar month, with one budget per expense group/month and a positive integer-centavo amount. No daily, yearly, or custom-period fields are introduced. Raw SQL and historical migration tests intentionally retain physical database names.

Bank keys are the lower-case bank name after trimming surrounding spaces and collapsing internal whitespace. The caller supplies the key; a database CHECK rejects a key that does not match that normalization. Migration `20261111130000_philippine_bank_catalog` adds a starter catalog based on Bangko Sentral ng Pilipinas listings and preserves entries with matching keys. [Universal and commercial banks](https://www.bsp.gov.ph/Statistics/Financial%20Statements/Commercial/assets.aspx) · [Digital banks](https://www.bsp.gov.ph/PaymentAndSettlement/PPDD_Payments_Bulletin.pdf) · [Rural banks](https://www.bsp.gov.ph/Statistics/Financial%20Statements/Rural/assets.aspx)

The Banks tab lets owners enable a catalog bank for their group and choose one or more payment methods they use with it. The expense form offers active assignments for the selected payment method. The server checks the same eligibility when a new bank is selected. Deactivation preserves the assignment, its method preferences, and historical expense links. Editing other expense details preserves the saved payment details. Deleting a group with no categories or budgets removes its bank settings in the same transaction.

`Expense.expenseGroupId` is backfilled from its category. Composite foreign keys to `Category(id, expenseGroupId)` and `BankAssignment(id, expenseGroupId)` enforce group consistency even outside the UI. The category's Prisma field maps to the physical `spendingId` column. These keys also prevent reparenting an assigned expense, category, or assignment into an incompatible group.

Existing bank text remains unchanged in the physical `Expense.bank` column, accessed as `legacyBankName` in Prisma, and `bankAssignmentId` initially stays null. No global bank or group assignment is inferred from historical text. Queries display the assignment's bank name when linked and otherwise display `legacyBankName`. Existing payment-method values remain untouched, including any historical combinations that future forms would not allow.

Category display names and totals are derived by queries/UI rather than duplicated as stored Salesforce formula/roll-up fields. Monthly budget keys and bank assignment keys use PostgreSQL composite uniqueness rather than concatenated strings.

Migration `20261115120000_recurring_expenses` adds the schedule and occurrence tables with row-level security and no Data API policies. The worker creates the expense, records its scheduled date, and advances the schedule in one transaction. Duplicating an expense group copies its ordinary expense history and starts with an empty Recurring tab.

## Planned financial-model dependencies

The initial Loans workflow persists `Loan`, `PayLaterAccount`, `RepaymentPlan`, `LoanInstallment`, `LoanPayment`, and `LoanPaymentAllocation`. The `20261120120000_loans` migration adds those tables and `PAY_LATER` while preserving existing expense data. Receiving and funding account names are recorded as text until the ledger is available. [Loans workflows](pay-later-and-loans-session.md)

Phase 1 uses the existing expense, budget, and recurring expense models. The following hierarchy covers the financial records proposed for Phases 2–4. [Dashboard and connected-finances roadmap](roadmap.md#dashboard-and-connected-finances)

### Proposed ownership hierarchy

Each top-level branch belongs to `User`. The indentation shows ownership and arrows show references across branches. The names describe responsibilities. The exact Prisma models, foreign keys, and migrations are open.

```text
User
├── ExpenseGroup (the existing Spending table)
│   ├── Category
│   ├── Expense → Category and optional BankAssignment
│   ├── Budget
│   ├── BankAssignment → shared Bank catalog
│   └── RecurringExpense → generated occurrences
├── FinancialAccount
│   ├── Cash, bank, e-wallet, and credit card accounts
│   └── Brokerage account → holdings, trades, and dated valuations
├── Loan (cash loan)
│   ├── Terms and repayment schedule
│   ├── Optional ExpenseGroup link
│   └── Disbursement link → transaction into receiving bank account or wallet
├── PayLaterAccount (reusable provider account, such as SPayLater)
│   └── RepaymentPlan → original Expense
│       └── Scheduled installments
├── FinancialTransaction
│   ├── Movements → financial accounts or liabilities
│   └── Payment allocations → loans, repayment plans, or installments
├── Bill or Payday Schedule
│   └── Expected occurrences → matched posted transactions
├── Goal (savings goal or sinking fund)
│   └── Allocations → FinancialAccount
└── Portfolio → linked brokerage accounts
```

The shared `Bank` catalog provides institution names. `BankAssignment` stores group-specific payment settings. A `FinancialAccount` carries a balance, so a user can have several distinct financial accounts at the same bank. The existing user-owned support records are Better Auth's `Account` and `Session`, plus `ReceiptScanner`. Better Auth's `Account` holds authentication identities. [Prisma schema](../server/db/schema.prisma)

### Loan and financed-purchase relationships

- **Cash loan.** `Loan` has its own owner, lender, terms, and repayment schedule. Its optional `expenseGroupId` must belong to the same user. A general loan can leave it blank. A linked group opens the same loan record. The disbursement transaction increases funds in the receiving account and records the amount owed.
- **Financed purchase.** Save the full purchase as one `Expense` with one linked `RepaymentPlan` under the reusable provider account. The plan gets its expense group from the original expense. Each purchase has its own schedule and outstanding balance, even when several purchases use the same provider.
- **Payments.** Record an actual payment once from the funding bank account or wallet. Allocations apply that payment to the corresponding plans or installments, including when a provider bill covers multiple purchases. Principal repayment reduces debt and is a cash outflow. Separately identified interest and fees count as expenses when posted. Purchases funded with cash-loan proceeds count toward the group budget as they occur.
- **History.** Duplicating an expense group can copy expense history without creating or copying payable balances. Corrections to a plan preserve its recorded payments. Validate ownership on both ends of every link between user-owned records.

The Loans area uses **Dashboard** for totals and upcoming payments and **Loan List** for individual cash loans and financed purchases. Expense groups provide purpose-based grouping for cash loans, and credit accounts group repayment plans by provider account. The provider balance is a rollup of the same plans shown in the list. [Pay Later and Loans design notes](pay-later-and-loans-session.md#loans-navigation)

Dashboard, cash-flow forecasts, and net worth use the underlying financial records to calculate their totals and projections. [Dashboard roadmap](roadmap.md#layout-and-acceptance-criteria)

| Planned capability | Required model behavior |
| --- | --- |
| Cross-group expense Dashboard | Aggregate only the owner's included groups and selected date range. Group duplication can copy history, so keep inclusion visible. Keep category identity tied to its group and report budget coverage explicitly. |
| Financial accounts and transactions | Support multiple accounts per institution, opening balances, income, expenses, linked transfers, and reconciliation. Link posted purchases to their expense records so cross-group reporting counts each purchase once. |
| Bills and paydays | Separate planned occurrences from confirmed transactions and match them without counting both. Existing recurrence occurrence records prove generation, not payment. |
| Goals | Allocate portions of real account balances, with funding/withdrawal history and limits against over-allocation. Earmarking is distinct from transferring funds. |
| Credit cards, cash loans, and Pay Later | Track liabilities, statement obligations, and payments. Derive outstanding balances and payoff progress from obligations and recorded payments. Dashboard totals count each obligation once. |
| Cash-flow forecasts | Derive dated projections from recorded balances and expected events, with explicit assumptions, scope, and freshness. Budget remaining alone cannot establish available cash. |
| Net worth and portfolios | Use assets minus liabilities and dated valuations. Count investments once across brokerage accounts and portfolio views. Distinguish contributions and withdrawals from investment returns. |
| Multi-currency reporting | Retain original amounts/currencies and explicit exchange-rate snapshots and dates. Never add raw amounts in different currencies. PHP remains the current implementation. |

Introduce financial-account and transaction storage additively, with a deliberate migration design. Preserve existing expense IDs, amounts, dates, ownership, and history. Do not infer opening balances from bank labels or reinterpret historical `BANK_TRANSFER` payment methods as confirmed internal transfers. Owners must deliberately map history and supply opening balances. Existing expenses not yet mapped to a financial account remain visible only to their expense-group owner; unclaimed groups remain hidden. Future global queries and mutations need the same server-side ownership enforcement as existing group features.

## Data-preserving rollout

Migration `20261022150000_core_expense_group_model` runs in one transaction. It adds the new tables, adds/backfills each expense's group ID, and strengthens foreign keys. It neither renames nor recreates the original tables, resets sequences, nor changes existing amounts, titles, dates, bank text, categories, or group names. Existing `/spending/[id]` URLs remain supported.

Back up the existing application rows and migration history before applying it. Afterward, compare all original columns per ID, verify the group backfill and null bank assignments, and reconcile counts/totals. Apply migrations before running the new application build, which reads the new optional bank relation. The previous deployed read/create-group workflows remain compatible with the retained physical tables. Older external expense writers would need to supply the new required group ID and are outside this app's current implemented workflows.

## Deferred

Email verification/delivery, password recovery, Google sign-in, and administrative assignment of preserved groups are deferred. Daily, yearly, and custom budget periods, exchange rates and original-currency snapshots, and user-configurable automation settings are deferred.

New expenses default to today's `Asia/Manila` calendar day. The existing timestamp column stores that day at UTC midnight, and `timeMinutes` stores the optional Manila clock time as minutes since midnight. The migration preserves existing timestamps and leaves their time field empty. Recurring expenses are generated with a date and an empty time. Budget months remain PostgreSQL DATE values.

## Authentication and ownership

`User`, `Session`, `Account`, `Verification`, and `RateLimit` map to Better Auth's lowercase database tables. Credentials and server sessions remain in our PostgreSQL database. Passwords are hashed by Better Auth; a user ID, not an email address or provider identity, owns expense groups. New provider support can reuse that stable ID later; implicit account linking is disabled.

Migration `20261024100000_user_auth_ownership` adds nullable `Spending.userId` and an indexed foreign key to `user.id`. Existing rows stay null and are excluded from every signed-in user's group list and direct group reads. New groups use the server-verified session user ID. Neither registration nor the first login can claim historical records. Ownership checks include each requested record ID, so knowing another user's ID grants no access.

RLS is enabled on business and authentication tables without adding Data API policies. The migration refuses preexisting policies on these tables, requiring explicit audited resolution before retrying. With no policies, this denies the Supabase `anon`/`authenticated` API roles. Prisma runs through a trusted server role that must own the tables or hold `BYPASSRLS`; it does not propagate Better Auth sessions as Supabase identities. Application-level ownership filters provide user isolation for that trusted role.

Migration `20261024100000_user_auth_ownership` was applied to the shared database on October 25, 2026 after an isolated backup restore was verified. All 25 original business rows remained unchanged apart from the new nullable ownership field; the five legacy groups retain null owners. RLS is enabled on all 11 business/authentication tables with no Data API policies. [PR #1](https://github.com/jcred97/redtally/pull/1) merged as `39be226038cb867de9a98fbfb357e013eace4236`, and the matching Vercel production deployment reached ready status. Production HTTP checks confirmed private access for two independent users, rejected cross-user group IDs, hidden legacy records, and revoked sessions after sign-out. Temporary verification records were removed.

Future schema releases still require backups, coordinated traffic, and verification against the matching application version. Email verification, password recovery, and Google sign-in remain deferred. See README for rollout instructions.
